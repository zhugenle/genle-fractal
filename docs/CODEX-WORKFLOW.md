# genle_fractal 的 Codex 协作工作流

目标是让公式、渲染、界面和发布任务主要修改各自的源码目录，并由一个集成任务把结果组合成可发布的网站。不同任务使用不同工作树；`dist/` 由构建生成，不作为开发入口。

## 1. 模块边界

| 目录 | 负责的内容 | 主要修改者 |
| --- | --- | --- |
| `src/formulas/<id>/` | `kernel.glsl` 公式计算，`definition.json` 元数据与接口版本，`parameters.js` 参数与默认值，`animation.js` 相位函数，`uniforms.js` 公式 uniform 上传 | 公式任务 |
| `src/renderer/` | 公共 GPU 管线、光照、材质、法线、阴影、画质、自适应性能与导出所需的渲染能力 | 渲染任务 |
| `src/ui/studio/` | 主页布局、控件、主题、样式、中英文本、页面 adapter 与暂时保留在 `render-loop.js` 中的动画时钟 | 工作室 UI 任务；时钟变更由集成任务协调 |
| `src/ui/nodes/` | 节点编辑器的布局、控件、页面 adapter 与交互表现 | 节点 UI 任务 |
| `src/state/` | 会话、预设存储与切换、相机、录制及持久化 | 状态任务或集成任务 |
| `src/contracts/` | 公式、渲染器、UI 与状态之间的接口约定 | 集成任务协调维护 |
| `config/build.json` | 当前公式选择、源码组合与构建配置 | 集成任务 |
| `scripts/` | 构建、检查、本地服务等开发工具 | 集成任务 |
| `public/` | 字体、图片、授权说明与其他静态资源 | 对应任务，新增资源时告知集成任务 |
| `release/` | 发布配置与发布说明 | 集成发布任务 |
| `dist/` | 构建产物，包括最终 HTML、JS、GLSL、CSS 和静态资源 | 构建生成；只有集成任务提交生成结果 |

根目录的产品、架构和协作文档也由集成任务协调更新。发布平台要求的 `.github/`、`.openai/` 等配置保留在其要求的位置，统一视为发布模块管理。

公式任务只描述形态与公式输出，不自己维护公共光照或页面。UI 消费 `parameters.js` 的参数组，不再复制另一份公式参数表；`definition.json` 声明元数据与 uniform 接口。渲染器通过接口接收公式与状态，不在公共渲染文件里写死某个公式的默认参数。

当前 ABI v1 是 UBER BULB 兼容接口：`kernel.glsl` 提供 `evaluateFormula` 的距离估计与轨道数据，`uniforms.js` 延续 A–I 的打包布局。它不是任意新公式的自动插入机制；需要不同 uniform、返回数据或着色要求时，由集成任务协调 adapter、页面接线和接口版本。

本轮为分阶段拆分。页面源码仍是有词法状态依赖的片段，由构建在一个 IIFE 作用域内组合；动画时钟暂在页面 adapter 的 `render-loop.js` 中，尚未全部移入 `src/state/`。改变片段顺序或把状态转换为显式 API 属于集成变更。

主工作室与节点页使用不同渲染 profile。节点页目前保留旧四档画质、固定材质与灯色、旧相位插值和原始性能策略；不能把主页面的五档画质、自适应或材质颜色行为直接视为节点页能力。需要统一时应另列兼容迁移任务。

`src/contracts/` 中的实际约定优先于本文中的示例。新增参数必须按该约定同时说明类型、单位、范围、默认值及是否参与动画或预设；不能依靠任务之间口头记忆。

## 2. Codex 中如何安排任务

推荐采用“一项任务、一个工作树、一条分支”。同一人可以先做公式任务，再做 UI 任务，不需要同时开五个窗口。

| 任务 | 分支名称示例 | 本地端口示例 | 交付内容 |
| --- | --- | --- | --- |
| 公式开发 | `feature/formula-<id>` | 4174 | 一个公式目录及接入说明 |
| 公共渲染优化 | `feature/renderer-<topic>` | 4175 | 渲染模块改动及画面、性能影响 |
| 工作室 UI | `feature/studio-ui-<topic>` | 4176 | UI 模块改动及交互说明 |
| 状态改动 | `feature/state-<topic>` | 4177 | 状态兼容方案及迁移说明 |
| 集成与发布 | `integration/<batch>` | 4173 | 合并后的源码、构建结果与发布记录 |

这些是分支和端口的命名示例，使用前确认端口未占用。节点 UI 有独立需求时再分配一个端口；不必预先占用全部端口。

在 Codex 中创建项目任务时选用工作树环境，从已经集成的架构基线开始。已有任务也可以继续在其独立工作树中工作。对每个任务的第一条指令写清：工作树路径、负责目录、允许修改的共享模块、预览端口和交付范围。

主目录 `D:\CodeX\web_release\web_fractal` 作为集成工作区。其他任务不要同时在这个目录直接改文件，也不要共用同一个浏览器预览地址来判断自己任务的结果。

`AGENTS.md` 中的目录规则帮助 Codex 判断文件归属，但它不是文件锁。可靠的隔离来自工作树，可靠的边界来自差异审查与自动检查。禁止在任务 A 的工作树里启动任务 B 的开发服务或提交任务 B 的改动。

## 4. 跨模块变更如何处理

如果公式增加了一个符合现有接口的参数，公式任务在 `parameters.js` 提供参数组与默认值，并在 `uniforms.js` 实现上传；涉及 uniform 声明时同时更新 `definition.json`。现有控件可以呈现参数组，但当前 UBER BULB ABI v1 还依赖既有变换、相位与参考字段。不同 uniform 布局、着色输出或启动要求都需要集成任务协调，不能只增加定义文件就假定任意公式已接入。

跨模块需求在交付说明或问题记录中写明以下内容：

1. 具体使用场景，例如“新公式需要三个独立轴向倍率”。
2. 新增或改变的输入输出：名称、类型、单位、默认值、范围。
3. 哪些模块必须修改，旧公式和旧预设会受到什么影响。
4. 最小可兼容方案，是否需要格式版本或回退行为。

集成任务确定接口并安排归属目录的任务实现。依赖任务从包含接口的提交同步，避免几个窗口各自创造相近但不同的字段。接口变更可以与消费它的代码在同一集成批次交付，但最终发布的提交必须包含完整实现。

发现其他模块的问题时，记录文件位置和现象，不顺手重写其他任务正在维护的文件。紧急修复也需由集成任务明确接管相关目录后执行，避免重复修改。

## 6. 合并、检查与构建

推荐集成顺序是：接口约定 → 状态和渲染能力 → 公式 → UI → 构建与发布。没有依赖关系的模块可以并行开发。

每个任务交付时提供：负责目录、分支与提交、变更目的、公共接口是否改变、已完成的检查、已知限制。交付内容应是源码差异；任务本地为预览生成的 `dist/` 不加入其交付提交。

集成任务从架构基线建立集成分支，按提交或分支逐项合并。每一步检查差异，拒绝无关目录改动，解决接口冲突后再合并下一项。只选择某个提交时，仍需检查它的实际文件范围，不能只依据提交标题判断。

以根目录 `package.json` 中的脚本为准，常用命令为：

```text
npm run check
npm run build
npm run check:dist
npm run dev -- --port 4173
npm run preview -- --port 4173
```

`dev` 用于开发预览，`preview` 用于查看已构建的网站。普通源码、资源与配置改变后会重新构建，浏览器刷新即可；服务脚本改变后需重启服务；构建脚本改变时，预览服务会按源码指纹加载新版构建器。不要在同一端口同时启动两个服务。脚本不应依赖某个用户 Documents 目录中的临时文件。

当前 CI 依次执行 `npm run check` → `npm run build` → `npm run check:dist`，校验源码、生成产物及来源清单是否一致。它不比较生成结果与 Git HEAD 中已提交的 `dist/`；提交产物的责任仍由集成任务承担。

检查与集成审查共同覆盖以下规则：

- 当前接入公式符合 `src/contracts/`，参数名和 uniform 不重复、默认值与范围有效；新增公式也按相同要求审查。
- 共享源码和入口引用完整，不引用工作树外的绝对本机路径。
- 构建可以从仓库源码与 `public/` 独立生成网站。
- `dist/` 的生成内容及来源清单符合当前源码与构建配置，避免手改产物与源码不同步。
- 发布流程使用该集成提交生成的产物，并记录对应提交。

新增行为的运行检查围绕用户可见结果进行。只做模块搬迁时，优先确认入口、资源加载、预设兼容和现有动画仍然正常；不为文件搬迁添加重复实现逻辑的测试。

## 7. 发布与回滚

发布任务先确认集成提交、构建产物和发布目标，再使用仓库现有流程上线。GitHub Pages 应在工作流中执行检查与构建，然后发布产物；Sites 则应提交对应源码版本并上传该版本的构建包。一次发布选定一种主流程，避免两个平台对同一地址分别部署不一致的版本。

允许自动发布的分支应由集成任务管理。公式、渲染和 UI 的开发分支推送仅用于保存或审阅，不能直接触发正式站点更新。若发布工作流会在主分支更新时自动部署，应在确认可以上线后才把集成分支合入主分支。

发布记录至少包含上线时间、地址、源码提交、平台版本或部署编号。私密凭据交给平台或本机安全机制保存，不写进源码、文档、预设 JSON 或发布包。

上线后出现问题时，优先回退到已确认的上一版本，或在主分支追加撤销相关集成改动的提交并重新构建发布。保留 Git 历史和其他任务分支，不使用强制推送覆盖协作成果。浏览器中已有预设应继续兼容；若无法兼容，在恢复发布前先处理数据迁移。

## 8. 日常使用的最短流程

1. 在 Codex 选一个负责目录明确的任务，使用独立工作树和端口。
2. 从最新架构基线开始，在源码模块内完成改动。
3. 需要跨模块能力时，记录接口需求并由集成任务协调。
4. 提交源码及交付说明，集成任务统一合并、检查和生成 `dist/`。
5. 在集成预览中确认整体结果，收到发布指令后统一上线。

这样，各窗口维护各自的源码，集成任务负责组合与发布，浏览器地址也能清楚对应到当前查看的工作树。
